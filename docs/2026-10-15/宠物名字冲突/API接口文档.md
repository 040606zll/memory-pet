# 宠物名字冲突修复接口说明

## 原因与行为

前端原来每次传 pet_name，默认为“小忆”；后端把它作为“用户设置的宠物名字”加入系统规则，没有区分浏览器显示值、用户当前命名和 MemoryOS 已确认命名，导致模型即使召回“羊狗”也坚持自称“小忆”。页面也没有接收模型解析后名字的字段。

名字的优先级调整为：最新用户消息的明确起名 > 本会话用户最近明确起名 > 已确认的宠物名字记忆 > 页面兜底名字。助手过去的自我介绍不能覆盖用户起名。命名冲突无法判断新旧时询问用户，不擅自选名；用户本人或其他动物的名字不能当成当前宠物名字。

## 接口

`POST /api/sessions/{session_id}/chat` 的请求字段保持兼容。请求 pet_name 现在明确表示页面的兜底称呼，不具有固定身份约束。

成功响应的 assistant_message 可增加一个字段：

```json
{"pet_name": "羊狗"}
```

含义是本轮实际采用的宠物名字，正文自称应与之保持一致。字段仅在宠物页面且模型提供合法名称时返回，省略时前端保持原显示。普通记忆助手页面忽略模型可能返回的宠物名字。

模型可选名字取首尾去空白后的 1–12 个 Unicode 字符，不接受控制字符；无效名字被忽略，有效回复正文仍然保留。该字段随现有消息 JSON 和操作结果保存，幂等重放不再调用模型，历史读取保留字段；没有新增列或表，因此无需数据库结构迁移。

## 页面与记忆边界

宠物页面用响应字段同步名字、标题、问候、等待提示、角色和头像标签，下一条新请求携带同步后的名字。不从回复正文或候选自由文本猜测名字。

浏览器昵称按登录账号隔离缓存；旧全局昵称不自动归给任何账号。缓存只用于显示和模型兜底，不表示 MemoryOS 已记住。明确起名可立即用于本会话，训练候选仍须确认后才调用原有 ingest。正式对话不生成训练候选。

手动改名保持原交互；请求等待期间的手动改名不会被迟到回复覆盖。打开旧历史不会用旧名字覆盖当前缓存。

## 部署

需同步后端 pet/schemas.py、providers.py、service.py 与前端构建产物。新增前端模块 petName.js 随构建打包。本次未改配置、依赖或启动脚本，未发布服务器；仅更新一端无法完整完成模型回复与页面同步。
